# 关于所谓"方舟前10费不准"的探索

## 叠甲

本人是一名萌新，对明日方舟及 Unity 引擎的底层运作方式了解有限，文中结论均来自本人通过黑盒实验构建的推断性理论。我无法断言费用条的运作机制一定如此，也不保证该理论能够适用于所有情形。

撰写本文的目的，是希望当非高难圈的玩家对这一说法感到困惑时，能在公开平台上找到一篇相对严谨的分析——而不必仅凭极限玩家们的口耳相传来摸索真相，再想方设法拼凑结论。知识应当共享，重复造轮子终究不是好事。若您对此问题有更深入、更准确的见解，欢迎批评指正。

## 背景

高难玩家大多听说过这样一个说法："明日方舟费用条的前10费是不准的"，甚至还会知道"第11费有31帧"。然而这些描述仍然相当模糊，例如：

- 在初始费用不同的地图上，这一现象会如何体现？
- 在不同的回费速率下，情况又会有何变化？
- 局内费用的消耗是否会对其造成影响？

本文将系统整理我对上述问题的探索过程与实验结论。

---

## 问题的本质

费用条的一次**循环**，是从空到满——即从 0 变化至 1——的过程。这一过程**不受费用数值变化的影响**，仅随时间自然推进（可露希尔、忍冬等干员对回费速度的影响将在后文单独说明）。因此，初始费用的多少，以及玩家消耗费用的操作，均不会改变费用条循环本身的节奏。

由此引出一个关键问题：**费用条的边界值（0 与 1）究竟归属于本次循环还是下一次循环？**

通常有两种处理方式：

- **左闭右开** `[0, 1)`：包含 0，不包含 1；
- **左开右闭** `(0, 1]`：不包含 0，包含 1。

以 30 帧/周期为例：

| 处理方式 | 各帧读数 |
|:--|:--|
| 左闭右开 | 0%, 3.3%, 6.7%, ……, 96.7%，（下一循环开始） |
| 左开右闭 | 3.3%, 6.7%, ……, 96.7%, 100%，（下一循环开始） |

两种方式的每个周期均为 30 帧，区别仅在于起止帧的归属。

---

## 实验结论：边界周期

明日方舟实际采用的处理方式出乎意料——**在开局若干个费用周期中，存在一个特殊的"边界周期"**，其行为与前后周期均不相同：

| 阶段 | 区间类型 | 说明 |
|:--|:--|:--|
| 边界周期之前（含第一周期） | 左闭右开 | 每个周期正好 N 帧 |
| **边界周期** | **左闭右闭** | **该周期比正常循环多出 1 帧** |
| 边界周期之后 | 左开右闭 | 每个周期正好 N 帧 |

### 边界周期的确定方法

根据实验，边界周期的判定规则如下：

> 在**仅计算符文修改**（即突袭/磨难的特殊效果、关卡描述中的红字、合约词条等；**不**计入可露希尔、忍冬等干员对回费速度的影响——该参数视为开局时即已确定）的回费速率下，**当逻辑帧数到达第 315 帧的那一刻，费用条正在经历的那个周期，即为边界周期**。

由此可以推导：在常规 30 帧/费的关卡上，第 315 帧恰好落在第 11 个周期内，边界周期即为第 11 周期——这也正是"第11费有31帧"这一说法的来源。

> **关于数字 315 的说明**：由于无法访问游戏源码，本文所有结论均来自黑盒测试。实际边界帧数目前仅能锁定在 [312, 315] 区间内，此处取 315 仅因其较为整齐，并非精确值。

## 这对费用条尺子意味着什么

本项目的尺子读取的是渲染出来的费用条宽度，而《明日方舟》的费用条在渲染上还有一个额外麻烦：非常靠近空条的前段宽度不可见。按当前观察，前约 `3.75%` 的费用条会被读成 `0`。

仍以 30 帧周期为例：

- 左闭右开时，尺子会看到类似 `0%, 0%, 6.7%, ..., 96.7%`，然后进入下一周期。
- 左开右闭时，尺子会看到类似 `0%, 6.7%, ..., 96.7%, 100%`，然后进入下一周期。

如果用边界前的校准配置去读取边界后的费用条，`0-29` 帧可能会被读成：

```text
0, 2, 3, ..., 28, 29, 29
```

反过来，如果用边界后的校准配置去读取边界前的费用条，`0-29` 帧可能会被读成：

```text
0, 0, 1, ..., 26, 27, 28
```

此外，不管校准配置是在边界前还是边界后生成，只要工具没有显式处理这个“边界周期多一帧”的现象，全局计时器在越过边界周期后都会相对真实时间偏移 1 帧。

## 本项目里的处理方式

对这个工具而言，关键不是争论游戏内部到底用了什么实现，而是让读数在实际使用时尽量贴近可观察现象。

从 2.4 起，尺子不再用「端点区间 + 魔数 315 边界帧 + 多 profile 交替」这套启发式去*近似*上述现象，
而是直接**复刻游戏内部的定点数（fp24，2^-24 截断）累加器**（见 `crates/ruler-core/src/fp24.rs`）：

- 三个定点量：`required`（费用回复所需数值，正常关卡 = 1.0）、`speed`（费用回复速度，正常 = 1/30；
  负费 = 1/60）、`accumulator`（已积攒计时器，从 0 起）。
- 每一逻辑帧 `accumulator += speed`；当 `accumulator + ε ≥ required`（ε ≈ 10^-5）时回复 1 费、
  `accumulator -= required`。
- 校准文件因此**只存一个标量 `required`**（`{ "format_version": 4, "required": 1.0 }`）。

「第 11 费 31 帧」这类边界周期、以及 X.5 回费速率下 38/37 的交替，都是这套定点截断算法的**自然结果**，
无需任何魔数或 profile 列表——`fp24.rs` 的单测 `normal_recovery_repeats_the_boundary_extra_frame_late`
直接从第一性原理复现了「第 11 周期 = 31 帧」并显示它会周期性再次出现（第 34962 帧又是 31）。上表的黑盒
实验数据现在被用作这套复刻算法的验证对照。

运行时引擎（`engine.rs`）每捕获一帧，就把 fp24 累加器**向前模拟**最少的帧数，使其渲染出的费用条像素
宽度与观测宽度最接近（乐观 0px），据此同步推进累加器与全局计时器。因此跨过开局边界周期后，全局计时器
**不再**相对真实时间偏移 1 帧——那一帧由 fp24 自然给出。

你可能仍会在 API 或界面里看到：普通周期是基础 `N` 帧，但跨过初始回费边界时，当前周期短暂显示为 `N+1` 帧。
这依旧是同一个现象，只是现在由定点累加器精确产生，而不是被特判补出来的。
