# 关于所谓“方舟前10费不准”的探索

## 结论先行

现在我们已经知道费用条循环的实际规则，不再需要用“左闭右开 / 左开右闭 / 边界周期切换”去黑盒拟合。

费用条内部有三个关键 fixed-point 参数，单位标准是 `2^-24`，运算按截断舍入：

| 参数 | 常规关卡 |
|:--|:--|
| 回 1 费所需数值 | `1.0 * 2^24 = 16777216` |
| 每逻辑帧回复速度 | `(1/30) * 2^24` 截断为 `559240` |
| 已积攒计时器 | 进入关卡时从 `0` 开始 |

游戏逻辑帧固定是 30 fps。每一逻辑帧，“已积攒计时器”增加“回复速度”；当它和“回 1 费所需数值”相差小于 `10^-5` 时，回复 1 费，并从计时器里减去“回 1 费所需数值”。由于这里用的是 fixed-point 截断，减完以后计时器可以是负数。

这个模型自然解释了“第 11 费有 31 帧”：常规回费速度每帧是 `559240`，30 帧只积到 `16777200`，比 `16777216` 少 16，但因为容差阈值是 `floor(10^-5 * 2^24) = 167`，前 10 个周期都能在 30 帧回费。每次回费后都会留下 `-16` 的残差，累计到第 11 个周期时，30 帧后还差 `176`，超过容差，所以这一周期需要第 31 帧。

因此，“前10费不准”并不是一个一次性的边界开闭规则，而是 fixed-point 误差累积的可观察结果。同样的额外帧还会在很久以后再次出现；常规 30f 下，下一个很晚的 31 帧周期会出现在第 34963 费附近。

## 速率调整对应哪一个参数

关卡外决定的回费速率调整，例如突袭、合约词条、关卡描述中的特殊规则，调整的是“回 1 费所需数值”。

关卡内发生的回费速率调整，例如可露希尔和忍冬，调整的是“每逻辑帧回复速度”。

本项目目前只对实际常见路径建模：正常状态使用 `559240`，识别到负费时使用半速 `279620`。如果之后要支持忍冬这类动态速度效果，需要在同一个 fixed-point 累加器上增加新的速度来源，而不是再引入新的“周期表”。

## 本项目里的实现方式

校准文件现在保存：

```json
{
  "format_version": 4,
  "timing_model": "fp24_accumulator_v1",
  "required_fp": 16777216,
  "profiles": [
    { "total_frames": 30 }
  ]
}
```

`required_fp` 来自校准得到的平均帧数。运行时分析每张截图时，尺子会：

1. 从上一张截图的 fixed-point 计时器状态开始。
2. 根据当前是否负费确定当前帧之后的回复速度。
3. 枚举截图之间可能经过的逻辑帧数。
4. 找出模拟费用条宽度最接近实际识别宽度、且最符合截图时间戳的候选。
5. 用这个候选更新内部计时器。

当截图第一次显示进入负费时，当前周期已经过的逻辑帧数不会按半速重新折算成两倍；已有 fixed-point 相位保持不变，只把后续到下一次回费的推进速度切到负费半速。

界面和 API 中的 `totalFramesInCycle` 不再是“某个静态 profile 的总帧数”，而是当前模拟状态下：

```text
当前循环已过帧数 + 到下一次回费还需帧数
```

所以它仍然会在常规第 11 费显示 31，也会在负费半速或 fixed-point 残差影响下显示动态周期长度。这个值的含义比旧的“边界周期补一帧”更直接：它就是当前模拟器认为距离下一次回费还需要多久。

## 为什么旧模型最终会漂移

旧实现把现象拟合成一次性的边界周期：边界前左闭右开，边界周期多 1 帧，边界后左开右闭。这个近似能解释早期样本，但它隐含了“额外帧只在一个边界附近发生”的假设。

fixed-point ground truth 说明，误差会一直随时间累积。第一次额外帧出现在第 11 费，之后还会在很长时间后再次出现。只靠一次边界切换，长时间运行后相位会逐渐向左漂，最终和真实费用条错开。

负费也同理。可露希尔这类局内效果改变的是每帧回复速度，不是把当前周期简单拉成两倍长度。如果在局内反复切换速度，必须保留同一个 fixed-point 计时器相位；重新套一张“负费周期表”会产生严重相位错误。
